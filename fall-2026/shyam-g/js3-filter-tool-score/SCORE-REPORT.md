What each row shows:
- **E1 (filter file).** v1.0.0 kept "Startup Founder" (8261337) on topic words alone. v1.1's
  role-word rule removes it. That's one posting, so +1/10.
- **E2 (setting).** Both "Product Manager, Hardware/Software" score exactly 3 (strong title, no topic
  word in the text) and are relevant by my label. Threshold 3 keeps them. On dev it changes nothing.
  **I'm not adopting it in this submission.** The threshold change was only measured, never decided
  on dev data, and I had seen these held-out titles before running it (section 3).
- **E3 (prompt).** Prompt A's relevance sentence ("supply chain, procurement, planning or ops analyst
  role") leaves out project/product manager, even though the persona's `target_titles` lists them.
  Claude followed the sentence over the persona fields. On 8281689 it wrote "the relevance rule
  requires a supply chain, procurement, planning or ops analyst role, and this is a software product
  management position" (`E3_prompt_A/8281689.json`). Prompt B adds the roles, and all 4 relevant
  postings flip to relevant. **The prompt was the bug, not the model.**
- **E4 (context).** Taking the posting text away changed no verdict on this set (7/10 → 7/10). The
  wrong answers stayed wrong for the same reason (prompt A's rule). Context mattered less here than
  the instruction.
- **E5 (tool list).** With the tool available, Claude called it in only 2 of 10 sessions
  (`transcripts/e5-tools-condition/`). On 8335610 the tool said `keep`, and Claude still said
  `not_relevant` ("an engineering project manager … not a supply chain role"). Adding a tool didn't
  change the score. The model decides whether to use it and whether to believe it.

## 3. What these numbers can't carry
- **n = 10.** One posting is 10 points. A 7/10 vs. 10/10 gap is 3 postings, and the exact binomial
  95% interval for 7/10 is roughly 35%–93%. These are not rates.
- **The held-out set was not blind to the builder.** Claude Code printed `labels/js1_hand_labels.csv`,
  held-out titles included, while building (2026-11-23), *before* prompt B and the threshold
  experiment existed. Prompt B's wording came from FILTER.md's persona line, not from the held-out
  titles. But I can't prove the choice wasn't influenced. Treat E2 and E3b as **contaminated**.
- **One sample per condition.** Claude's verdicts can vary between runs (JS1's sampling study showed
  that). I didn't repeat the runs, so run-to-run variance is not measured here.
- **All 20 labels are formlabs.** Nothing here speaks to spotify or palantir, where every posting failed the location gate.
- The labels are from JS1 (October), under a looser idea of relevance than FILTER.md. Dev has
  "Engineering Technician, Boston" as relevant. That's why dev agreement is stuck at 6/10 for every filter version.

## 4. What persistence is not proof of
If the agent behaves differently in a new session, **nothing has been trained.** In this project:
- The MCP tool re-reads FILTER.md on every call. Editing the filter changes every later session's
  answers with no model change. That's persistence through a **file** (context), not learning.
- Claude's verdicts changed between E3a and E3b because the **prompt** changed. Run E3a again
  tomorrow and you get the old behavior back. Nothing carried over.
- `claude -p` run inside the project folder saw the git status and answered about the repo
  (2026-11-23). That's the harness adding **context**, not memory in the weights. That's why
  `js3/claude_cli.py` runs Claude from an empty temp folder.
- A change that persists across sessions can come from files, prompts, settings, tool lists, or the
  harness. Only a change to the weights is training. None of my experiments touched weights, and
  none could.
